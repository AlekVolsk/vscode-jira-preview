# Development

## Layout

- `out/parser.js` — Jira wiki markup → HTML parser. A fork of `markupParser` from `denco.confluence-markup` (MIT, © Denis Baumgärtner).
- `out/formatter.js` — the `.jira` formatter. Plain Node, no `vscode` import, so it runs under the test runner.
- `out/extension.js` — webview host, resource resolution, commands, the title-bar button and the formatting providers.
- `media/jira.css` — preview styles.
- `lib/hljs/` — a vendored subset of highlight.js: the core plus the sixteen language definitions the preview registers. The full package is 9.4 MB and this is 264 KB, and vendoring keeps the extension free of runtime dependencies, which is why it is a copy rather than a `dependencies` entry. Language definitions carry no requires between them, so the subset is self-contained; refresh it by copying `lib/core.js` and `lib/languages/<name>.js` out of a current highlight.js.
- `syntaxes/jira.tmLanguage.json` — TextMate grammar for the editor. Generated by hand; `test/grammar.test.js` runs it through the same engine VS Code uses.
- `images/icon.svg` — icon source; `images/icon.png` is generated from it.

## Tests

```bash
npm test
```

`node --test` over `test/`, no dependencies for the formatter and parser suites. The grammar suite needs `npm i vscode-textmate vscode-oniguruma` and skips itself when they are absent. `test/vscode-stub.js` stands in for the `vscode` module so the parser runs outside the extension host. The formatter and the parser are covered; the webview host is not.

## Build

```bash
npm run build
# or, with an explicit output name:
npx --yes @vscode/vsce package --no-dependencies -o jira-preview.vsix
```

Install the result locally:

```bash
code --install-extension jira-preview.vsix
```

The PNG icon is generated from `images/icon.svg` with [`sharp`](https://www.npmjs.com/package/sharp) — that is the only reason `node_modules/` exists here, and it is not needed at runtime.

## Invariants — do not break these

- **All webview resources go through `webview.asWebviewUri()`**, with `webview.cspSource` in the Content-Security-Policy and `localResourceRoots` set to the open file's folder, the workspace folder and `extensionUri`. Hardcoding the webview authority (which is what the existing Confluence-markup extensions do) breaks local images on remote and WSL windows — that is the reason this extension exists as a fork rather than a configuration of an existing one.
- **Preview font size comes from `--vscode-editor-font-size`**, so it follows the editor setting instead of a fixed value.
- **Images and attachments resolve relative to the folder of the `.jira` file**, which is how a Jira export lands on disk.
- **Code is coloured in the extension, not in the webview.** The CSP is `default-src 'none'` with no `script-src`, and it stays that way: highlight.js runs in the extension host and the webview receives finished markup. The body reaches `highlightCodeBlocks` with `<` already escaped by the parser, so it is unescaped before highlighting and highlight.js escapes its own output.
- **The table of contents is built from the finished HTML, not while lines are parsed.** By then a heading carries its inline markup, and the ones that only look like headings — inside `{code}` — are escaped and invisible to the pass. It is also the reason `<details>` does the collapsing: the CSP admits no script, and this needs none.
- **Order inside the inline pass is load-bearing.** What can be swallowed runs first: `{{ }}` becomes `<code>` ahead of everything, `{*}` and `{+}` are unwrapped next, then attachments, links and images, and only then `+underline+`, `^sup^` and `~sub~` — because `[^file.xlsx]` carries a caret that `^…^` would otherwise pair with the caret of the next attachment on the line. `bq.` and `??cite??` stay unguarded ahead of the links: their `(.*)` has to reach across a whole line, which segmenting on tags would cut short.
- **`replaceOutsideHtml` wraps every inline replacement, not just the emphasis ones.** `{{ }}` becomes `<code>` early in the pass, and a replacement that runs unguarded afterwards reaches inside it — which is how `{{sample.results[field_id]}}` grew a link. The image replacement had to stop assigning the whole line for this to be possible; that it also stopped swallowing text next to an image is a side effect, not the goal.
- **Inline markup is applied to text only.** The parser rewrites a line in place, so by the time `*bold*`, `_italic_` and `-strike-` run, the line already holds `<a href=…>`, `<img src=…>` and `<code>` — all of which carry `_` and `-` that are not markup. `replaceOutsideHtml` feeds the replacements the text between tags; without it the choice is between mangled hrefs and markup that silently stops working, which is what it used to do.
- **Formatting is idempotent.** Formatting an already formatted document must produce the same text; a rule that keeps changing its own output would fight format-on-save. There is a test for it, and any new rule belongs in it.
- **A fence's role comes from its parameter, not from a running count.** Jira writes `{code:lang}` only when opening and a bare `{code}` when closing, so an opening fence met while a block is open means a closing fence was lost. Counting fences pairwise instead would silently swallow whatever sits between them — on a real export that was a heading and two paragraphs.
- **The notice is cut by its own text, not by position.** An earlier version tracked which line followed an opening fence, and its idea of the blocks drifted from the role pass on a file whose fences were unbalanced — leaving one notice uncut and the formatter not idempotent.
- **Fences are repaired before anything else reads the document.** `repairFences` runs first and hands the rest of the formatter a document whose blocks balance; every later stage may assume a fence line is a whole line. This is also what keeps the formatter and the parser agreeing on where code starts: the parser toggles on `{code}` anywhere in a line, the formatter only on a whole line, and Jira's notice welds a literal `{code}` into the body — which is exactly how the two drift apart on a broken file.
- **A block glued to a list item belongs to that item.** A `{quote}`, `{panel}` or `{code}` fence right under a list line (or its continuation), with no blank line between, is nested in the `<li>` by the parser, and the formatter inserts no blank line before it or between its closing fence and the next item — a blank line there ends the list in Jira. Blank lines the author wrote are kept. A panel or quote body keeps its own list state, and a blank line inside a code block is code, so neither closes the list around the block.
- **`{code}` and `{noformat}` bodies are copied byte for byte,** once the fences are repaired. Everything the formatter does — trimming, blank lines, markup cleanup — stops at those fences. Range formatting refuses to run at all when the selection starts inside one, since a fragment cannot tell it is inside a code block.
- **Cleanup never changes what Jira renders.** `{}` is dropped only where it is not separating two markup tokens, and `{*}text{*}` is unwrapped only where the neighbouring characters let the bare delimiter render — the escaped form exists precisely because they sometimes do not.

## Manifest identity

`publisher` and `author` are `AlekVolsk`, case-sensitive. VS Code normalizes the internal extension id to lowercase (`alekvolsk.jira-preview`) — that is expected, not a mismatch.

## Distribution

Releases are published on GitHub with the `.vsix` attached; that is the intended distribution channel. Marketplace publishing is not used. Open VSX would be a possible registry alternative, but is not set up.

## Icon and licensing

The parser fork keeps its MIT copyright in `LICENSE.txt`. The icon combines the official Jira mark with an eye badge — acceptable for GitHub distribution, but it would be a trademark risk for store publication.
